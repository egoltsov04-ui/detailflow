# Переезд на собственный сервер

Целевая архитектура и детали: `references/architecture.md`. Порядок этапов: `references/migration-steps.md`. Прочитай их до начала работы.

## Главные правила

- Сначала staging (локально в WSL2 + Docker Desktop, затем второй стек на сервере), потом production. На боевое ничего не запускай без моего подтверждения.
- Любой скрипт по умолчанию работает в режиме dry-run, реальное действие только с явным флагом.
- Секреты только в `.env` на сервере и в менеджере паролей, не в репозитории, не в чате, не в логах.
- Не удаляй проекты Vercel и Supabase Cloud, пока новый сервер не работал стабильно 14 дней и откат не проверен.
- Каждый шаг заканчивается проверкой: что запущено, что открывается, что в логах. Скажи мне простыми словами, что сделано и что делаю я руками (покупки, DNS, оплата, ключи).

## Главная техническая задача

Маршруты в `api/` написаны под Vercel Functions (обработчик с req/res, лимит 60 секунд у `send-reminders.ts`). Нужно:

1. Прочитать все файлы `api/` и составить список маршрутов, переменных окружения и внешних вызовов.
2. Создать маленький Node-сервер (Express или Hono, выбери проще и опиши причину), который монтирует те же обработчики по тем же путям, без переписывания бизнес-логики. Общий код остаётся в `server/lib/`.
3. Расписания: Vercel Cron не используется. `send-reminders` уже вызывается раз в минуту из базы через pg_cron + pg_net с `Authorization: Bearer CRON_SECRET` (`supabase/deploy/configure_notification_cron.sql`, адрес и секрет в Supabase Vault: `detailflow_app_url`, `detailflow_cron_secret`). На self-hosted Supabase оставь этот же способ: включи pg_cron, pg_net и Vault, запиши новые значения в Vault и примени тот же SQL. Проверь, как сейчас работает автозакрытие смен (есть ли для него расписание), и если нужно, добавь его тем же способом.
4. Фронтенд собирается `vite build` и отдаётся Caddy как статика, `/api/*` проксируется на Node-сервер.
5. Auth, Storage и PostgREST идут на self-hosted Supabase. Меняются только `VITE_SUPABASE_URL`, ключи и `APP_URL`.
6. E2E тесты прогоняются против нового стека до переключения.

## Бэкапы

Существующие скрипты `scripts/weekly-encrypted-backup.mjs` и `scripts/backup-preflight.mjs` рассчитаны на Cloudflare R2. Перенастрой на Backblaze B2 (S3-совместимый API или rclone с шифрованием), сохрани шифрование. Обязательно: восстановление на чистой базе по инструкции, замер времени, запись результата в `docs/`. Бэкап, который не восстанавливали, считается несуществующим.

## Безопасность сервера

SSH только по ключам, вход root и пароли отключены, UFW открывает 22 (желательно с ограничением по IP), 80, 443. Fail2ban. Автообновления безопасности. Порты Postgres и Studio наружу не открывать (Studio только через туннель или базовую авторизацию в Caddy). Docker-тома на диске с запасом, мониторинг места и uptime-проверка снаружи.

## Что делаю я, а не ты

Покупки и оплата (Contabo, Backblaze, домен), DNS у регистратора, создание ключей в панелях, хранение резервных ключей шифрования. Всегда проси меня об этом отдельным пунктом с точной инструкцией.
