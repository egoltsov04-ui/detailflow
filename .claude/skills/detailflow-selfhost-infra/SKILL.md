# Переезд на собственный сервер

Целевая архитектура и детали: `references/architecture.md`. Порядок этапов: `references/migration-steps.md`. Прочитай их до начала работы.

## Главные правила

- Сначала staging (локально в WSL2 + Docker Desktop, затем второй стек на сервере), потом production. На боевое ничего не запускай без моего подтверждения.
- Любой скрипт по умолчанию работает в режиме dry-run, реальное действие только с явным флагом.
- Секреты только в `.env` на сервере и в менеджере паролей, не в репозитории, не в чате, не в логах.
- Не удаляй проекты Vercel и Supabase Cloud, пока новый сервер не работал стабильно 14 дней и откат не проверен.
- Каждый шаг заканчивается проверкой: что запущено, что открывается, что в логах. Скажи мне простыми словами, что сделано и что делаю я руками (покупки, DNS, оплата, ключи).

## Главная техническая задача

Маршруты в `api/` написаны под Vercel Functions (обработчик с req/res, лимит 60 секунд у `send-reminders.ts`). Нужно:

1. Прочитать все файлы `api/` и составить список маршрутов, переменных окружения и внешних вызовов.
2. Создать маленький Node-сервер (Express или Hono, выбери проще и опиши причину), который монтирует те же обработчики по тем же путям, без переписывания бизнес-логики. Общий код остаётся в `server/lib/`.
3. Расписания: Vercel Cron не используется. `send-reminders` уже вызывается раз в минуту из базы через pg_cron + pg_net с `Authorization: Bearer CRON_SECRET` (`supabase/deploy/configure_notification_cron.sql`, адрес и секрет в Supabase Vault: `detailflow_app_url`, `detailflow_cron_secret`). На self-hosted Supabase оставь этот же способ: включи pg_cron, pg_net и Vault, запиши новые значения в Vault и примени тот же SQL. Проверь, как сейчас работает автозакрытие смен (есть ли для него расписание), и если нужно, добавь его тем же способом.
4. Фронтенд собирается `vite build` и отдаётся Caddy как статика, `/api/*` проксируется на Node-сервер.
5. Auth, Storage и PostgREST идут на self-hosted Supabase. Меняются только `VITE_SUPABASE_URL`, ключи и `APP_URL`.
6. E2E тесты прогоняются против нового стека до переключения.

## Бэкапы

Существующие скрипты `scripts/weekly-encrypted-backup.mjs` и `scripts/backup-preflight.mjs` рассчитаны на Cloudflare R2. Перенастрой на Backblaze B2 (S3-совместимый API или rclone с шифрованием), сохрани шифрование. Обязательно: восстановление на чистой базе по инструкции, замер времени, запись результата в `docs/`. Бэкап, который не восстанавливали, считается несуществующим.

## Безопасность сервера

SSH только по ключам, вход root и пароли отключены, UFW открывает 22 (желательно с ограничением по IP), 80, 443. Fail2ban. Автообновления безопасности. Порты Postgres и Studio наружу не открывать (Studio только через туннель или базовую авторизацию в Caddy). Docker-тома на диске с запасом, мониторинг места и uptime-проверка снаружи.

## Что делаю я, а не ты

Покупки и оплата (Contabo, Backblaze, домен), DNS у регистратора, создание ключей в панелях, хранение резервных ключей шифрования. Всегда проси меня об этом отдельным пунктом с точной инструкцией.

## Чек-лист безопасности переезда (20 правил владельца)

Проходи его перед запуском staging на сервере и ещё раз перед переключением production. По каждому пункту отчитайся: выполнено, как проверено, что осталось. Пункты, которые закрывает сам Supabase, всё равно проверь на нашем стеке, а не по документации.

1. **API-ключи спрятаны.** Секреты только в `deploy/selfhost/.env` на сервере (права 600) и в менеджере паролей. В `VITE_*` и в `dist/` только публичный ключ: проверь `grep` по собранному `dist/`.
2. **Секретов нет в Git.** Перед переездом прогони поиск по всей истории (`git log --all -p`) на JWT, `service_role`, приватные ключи. Найденное: отозвать ключ и сгенерировать новый, переписывать историю только с подтверждения владельца.
3. **В браузере только публичный ключ БД.** `ANON_KEY` во фронтенде, `SERVICE_ROLE_KEY` только в контейнере API. Для нового стека генерируй новые ключи, старые не переноси.
4. **RLS включён везде.** Запрос к `pg_tables`: в схеме `public` нет таблиц без RLS. `scripts/tenant-isolation.test.mjs` зелёный против нового стека.
5. **Чувствительные данные зашифрованы.** Диск и бэкапы (age), секреты расписания в Vault, TLS на всех внешних соединениях. Телефоны и email клиентов не пишутся в логи.
6. **Авторизация проверяется на сервере.** Каждый маршрут `api/` и каждый RPC сам проверяет сессию и роль, скрытие кнопок не считается.
7. **Доступ к записям ограничен студией.** `studio_id` / `tenant_id` берётся из сессии, тесты изоляции студий и ролей (мастер, адміністратор без финансов) проходят.
8. **Подмена полей заблокирована.** Клиент не может записать себе `tenant_id`, роль, `is_internal`, цену или ставку: только через RPC с проверкой, прямые `update` этих колонок запрещены (миграция 062, триггеры).
9. **Сессия защищена.** Supabase хранит токен в браузере, не в cookie: значит строгая CSP без внешних скриптов, короткий срок access-токена, отзыв refresh-токенов при выходе и смене пароля.
10. **Пароли хэшируются.** Хэширует GoTrue (bcrypt), в наших таблицах паролей нет. Проверь, что минимальная длина пароля задана в настройках Auth.
11. **Частота входа ограничена.** Лимиты GoTrue (`RATE_LIMIT_*`) включены на self-hosted стеке, плюс ограничение в Caddy на `/auth/v1/token` и fail2ban по логам Caddy.
12. **Защита от ботов.** Онлайн-запись и регистрация: текущие лимиты по IP и студии, при спаме добавить капчу (Turnstile или hCaptcha) в GoTrue и в форму записи, с согласия владельца.
13. **Запросы параметризованы.** Только supabase-js / PostgREST и RPC. В PL/pgSQL динамический SQL только через `format('%I', ...)` и `using`, без склейки строк с вводом.
14. **Весь ввод валидируется.** На сервере и в базе (check-ограничения, проверки в RPC), а не только в форме.
15. **Пользовательский контент экранируется.** React экранирует сам, `dangerouslySetInnerHTML` не используем (сейчас 0 мест). Письма SendPulse: экранировать имя клиента, авто, заметки.
16. **Загрузка файлов ограничена.** Бакет `job-photos` приватный, 8 МБ, только JPG, PNG, WebP, путь проверяется `can_access_job_photo`. На S3 то же самое, плюс лимит в Caddy на размер тела.
17. **Ответы API обрезаны.** Наружу не уходят тексты внутренних ошибок, стектрейсы, лишние колонки (ставки без права на финансы). Node-сервер уже отвечает `Internal error`, проверить каждый маршрут.
18. **Security headers.** Есть в Caddyfile: nosniff, Referrer-Policy, X-Frame-Options, Permissions-Policy. Добавить на сервере HSTS и Content-Security-Policy, проверить, что приложение и push с ними работают.
19. **HTTPS принудительно.** Caddy выдаёт сертификаты и перенаправляет HTTP на HTTPS, `APP_URL` только `https://`, Supabase и Studio наружу только через Caddy.
20. **Зависимости сканируются.** `npm audit --omit=dev` перед каждым релизом, обновление образов Supabase через `update.sh` после бэкапа, Dependabot или CI-шаг на аудит.
