# Безопасность Detailflow

Главный риск продукта: одна студия видит или меняет данные другой. Клиент браузера использует anon-ключ, поэтому защита держится на RLS, правах RPC и серверных проверках, а не на интерфейсе.

## Порядок проверки

1. **Изоляция студий.** Найди все таблицы с данными студии (`supabase/migrations/`). У каждой должны быть `studio_id`, включённый RLS и политики на SELECT, INSERT, UPDATE, DELETE. Таблица без политик при включённом RLS закрыта, без включённого RLS открыта. Проверь оба случая.
2. **RPC и функции.** Для каждой `SECURITY DEFINER` функции: фиксированный `search_path`, студия определяется из `auth.uid()`, а не из аргумента, `REVOKE ALL FROM PUBLIC` и точечный `GRANT` нужным ролям. Функции для anon (публичная запись) отдельно: что именно они возвращают и пишут.
3. **Матрица ролей.** Владелец, адміністратор (с флагом финансов и без), майстер, support. Для каждой роли проверь: что видит, что меняет, что не должен видеть (зарплаты, финансы, чужие заказы у майстра). Проверка должна быть на сервере и в RLS.
4. **Storage.** Бакет `job-photos` приватный, путь начинается с `studio_id/`, политики проверяют префикс, доступ к файлам через подписанные ссылки с коротким сроком. Загрузка: проверка типа по содержимому, лимит размера, имя файла генерируется сервером.
5. **Импорт CSV/XLSX.** Лимит размера и строк, защита от формульных инъекций при экспорте (значения, начинающиеся с `=`, `+`, `-`, `@`, экранировать), валидация телефонов и сумм.
6. **Публичные эндпоинты** (`api/public`, `api/booking-requests`; ограничение частоты уже есть: миграция 060 и `server/lib/publicBookingRateLimit.ts`, проверь, что оно работает): лимит запросов по IP и по студии, валидация входа, нет утечки списка клиентов или занятых слотов сверх нужного, капча или токен при злоупотреблении.
7. **Секреты.** В `VITE_*` только публичные значения. `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`, SendPulse, VAPID private, WayForPay secret только на сервере. Поиск в истории git и в логах. Cron-эндпоинты требуют `CRON_SECRET`.
8. **Аудит-лог.** Критичные действия (удаление, изменение цен, финансов, ролей, экспорт) пишутся в лог с `studio_id`, пользователем и временем.
9. **Тесты изоляции.** Для каждого найденного риска добавь автоматический тест: пользователь студии A пытается прочитать и изменить данные студии B через клиент, через RPC и через Storage, ожидаемый результат отказ.

## Правила работы

- Всё только на staging и локальной базе. Боевую базу не трогай. SQL в `supabase/audits/` только для чтения.
- Ничего не чини молча. Сначала отчёт, затем исправления по моему подтверждению.
- Не выводи значения секретов, только факт наличия и место.

## Формат отчёта

Для каждой находки: серьёзность (критично, высоко, средне, низко), где (файл и строка или объект БД), как воспроизвести, чем грозит простыми словами, как исправить. Сверху краткий итог: сколько находок по уровням и что исправить первым. В конце список того, что проверено и чисто, и что не удалось проверить.
