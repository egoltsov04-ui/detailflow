# База данных Detailflow

В репозитории миграции `supabase/migrations/001-061`. Новые миграции нумеруются дальше (062 и далее), существующие не редактируй.

## Правила миграции

1. Один файл на одну логическую задачу, имя `NNN_короткое_описание.sql`, следующий номер после последнего в папке (проверь сам, не угадывай).
2. RLS и политики для новой таблицы пишутся в той же миграции, что и таблица. Таблица с данными студии: `studio_id uuid not null`, индекс по `studio_id`, внешний ключ.
3. Деньги только `numeric(12,2)` (или точнее по задаче), никогда float. Время `timestamptz`, хранение в UTC, показ в часовом поясе студии.
4. Миграция идемпотентна там, где это возможно (`if not exists`), без `drop` данных. Деструктивные изменения разбиваются на этапы: добавить, перенести, переключить код, и только потом удалять в отдельной миграции после моего подтверждения.
5. Для каждой миграции, которая меняет схему, добавь файл отката в `supabase/rollback/` с тем же номером.
6. `SECURITY DEFINER` функции: фиксированный `search_path`, студия из `auth.uid()`, явные `REVOKE`/`GRANT`.
7. Индексы под реальные запросы: фильтры по `studio_id` и дате, поиск клиентов по телефону. Не создавай индексы «на всякий случай».
8. Часовой пояс, валюта и язык берутся из настроек студии, не из констант.

## Порядок работы

1. Прочитай последние миграции и `supabase/audits/migration_inventory.sql`, пойми текущее состояние.
2. Запиши план: что меняется, какие данные затронуты, как откатить.
3. Напиши миграцию и откат.
4. Примени на локальной базе или staging. Проверь, что старый функционал работает: прогони E2E.
5. Проверь изоляцию: пользователь студии A не видит данные студии B (см. скилл `detailflow-security-review`).
6. Покажи мне результат и жди подтверждения перед любым применением к боевой базе. Боевую базу сам не трогай.

## Аудиты

SQL для проверок живёт в `supabase/audits/` и только читает данные (`select`). Никаких `update`, `delete`, `drop` в аудитах.
