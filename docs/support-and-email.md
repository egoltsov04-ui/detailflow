# Доступ поддержки и письма регистрации

Служебный вход расположен по `/admin` на основном домене сервиса. Регистрация студии не выдаёт права поддержки.

## Первое подключение поддержки

1. Выполнить `supabase/migrations/031_support_applications.sql` целиком в SQL Editor. Скрипт допускает повторный запуск.
2. Создать отдельного пользователя через Supabase Authentication → Users → Add user. Можно пригласить его письмом после настройки SMTP. Не используйте email действующего владельца или мастера.
3. В `supabase/deploy/grant_support_account.sql` заменить `support@example.com` на служебную почту и выполнить запрос. Он отказывается менять роль существующего владельца/мастера и ничего не делает при повторном назначении поддержки.
4. Войти этим пользователем по `/admin`. Если уже открыт другой аккаунт, выйти или использовать отдельный профиль браузера.

Поддержка видит заявки, контакты и факт подтверждения email. Активация доступна после подтверждения email; она атомарно создаёт студию, владельца, настройки и пробную подписку. Повторная активация не создаёт дубль. Для отказа обязательна причина. Права проверяются в базе при каждом действии. Самостоятельное создание студии старым RPC закрыто: теперь требуется решение поддержки.

## Если письмо не пришло

Регистрация вызывает Supabase Auth напрямую. Переменные SENDPULSE_API_* в Vercel не настраивают SMTP Supabase Auth.

В Supabase проверьте Authentication → Users: существует ли адрес, подтверждён ли email и был ли отправлен запрос подтверждения. Повторная регистрация уже существующей почты может возвращать нейтральный успешный ответ без нового письма. В таком случае следует войти в существующий аккаунт, а не регистрировать его снова.

В Authentication → Email / SMTP Settings настройте собственный SMTP: сервер, порт, логин, пароль и разрешённый адрес отправителя. Используйте SMTP-реквизиты провайдера, не API-ключ приложения. Встроенная почтовая служба Supabase ограничивает получателей участниками команды проекта и не предназначена для production.

В Authentication → URL Configuration укажите основной HTTPS-домен как Site URL и разрешите адреса возврата `/login` и `/admin`. Код регистрации и повторного запроса письма передаёт `/login` явно. Проверьте Auth Logs на ошибки отправки и ограничения частоты. После исправления настроек используйте кнопку повторной отправки на странице подтверждения email.

Безопасная диагностика (не возвращает пароли или токены):

```sql
select email, created_at, email_confirmed_at, confirmation_sent_at, last_sign_in_at
from auth.users
where lower(email) = lower('email-to-check@example.com');
```

https://supabase.com/docs/guides/troubleshooting/not-receiving-auth-emails-from-the-supabase-project-OFSNzw


## Письма мастерам из кабинета владельца

В разделе «Команда» → «Доступ до кабінету майстра» доступны первое приглашение, повторный запрос письма и восстановление пароля. Для привязанного пользователя используется email из Supabase Auth. Повторное письмо существующему аккаунту отправляется как ссылка создания нового пароля; пароль меняет сам мастер после перехода. Заблокированным мастерам письма не отправляются. Для непривязанного профиля можно указать email и повторить приглашение после ошибки SMTP.

Адрес возврата берётся из APP_URL, затем WAYFORPAY_APP_URL или VERCEL_PROJECT_PRODUCTION_URL. В Supabase URL Configuration разрешите `/login?role=master&activate=master` на основном домене. Клиент и сервер ограничивают повторный запрос интервалом в минуту; Supabase может применять дополнительные ограничения. Успешный ответ означает принятие запроса почтовой службой, а не подтверждённую доставку во входящие.

Проверки обновления: TypeScript приложения/API, production build, регрессии импорта и серверного обработчика писем с подставной почтовой службой. На локальном стенде проверены 24 раздела при 360/390 px и импорт с переходом к сохранённым тестовым клиентам. Отправка реальных писем требует проверки настроенного SMTP.
