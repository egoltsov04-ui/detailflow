# Эксплуатация Detailflow

## Проверки перед выкладкой

1. `npm ci`, `npm run lint`, `npm test`, `npm run build`. CI выполняет эти команды для main и pull requests.
2. Проверить SQL на отдельной базе. Миграции 033–044 повторяемые; пакет обновления содержит одну общую транзакцию.
3. Сохранить резервную копию перед применением SQL в production. Сначала обновить базу, затем frontend/API.
4. После выкладки проверить `/api/health`: HTTP 200 и `{"status":"ok"}` означают доступность БД и ключевых новых объектов. Это не проверка SMTP или оплаты у провайдера.
5. Проверить два аккаунта в разных сессиях: владелец и мастер. Третьей сессией проверить администратора без финансовых прав, затем выдать и отозвать доступ.

## Резервное копирование и восстановление

Настройку автоматических резервных копий и срок хранения в рабочем Supabase нужно проверить в панели проекта. Наличие SQL-файлов в Git не является резервной копией данных. Автоматические копии production в этой задаче не включались и не проверялись.

Ручная резервная копия PostgreSQL: установите клиент PostgreSQL соответствующей версии и настройте отдельный профиль подключения `detailflow_backup` в pg_service.conf; пароль храните в pgpass с ограниченными правами, а не в Git/аргументах команды. Запускайте:

```powershell
pg_dump --dbname=service=detailflow_backup --format=custom --no-owner --no-acl --file=detailflow-backup.dump
pg_restore --list detailflow-backup.dump
```

Файл содержит персональные и финансовые данные. Хранить зашифрованным вне репозитория, доступ только обслуживающему администратору. В приложении нет автоматической загрузки этих данных во внешнее хранилище.

Проверка восстановления: создать отдельную пустую тестовую базу/проект; проверить, что профиль `detailflow_restore_test` указывает именно на неё; восстановить копию туда, без `--clean` и без обращения к production. Для нового проекта Supabase учитывать управляемые схемы Auth/Storage и версии расширений; конфликтующие объекты не удалять автоматически. Записать дату, объём, контрольные количества клиентов, авто, работ, начислений и чеков. Проверить вход тестового пользователя, изоляцию студий и полный цикл работы. Удалять тестовые персональные данные только после проверки и по утверждённой процедуре.

Файлы Storage (фотографии работ) требуют отдельной копии: SQL содержит метаданные, а не байты изображений. Ключи проекта, SMTP и Vercel environment variables также не входят в pg_dump. Отдельно хранить конфигурацию без открытых секретов.

## Аудит и доступ

Изменения клиентов, автомобилей, мастеров, ролей, подписок, работ, начислений, выплат, оплат и чеков фиксируются в `audit_logs`. Полные снимки доступны только владельцу своей студии; мастер и администратор без прав не смогут получить зарплаты через журнал. Запрещено редактировать аудит через клиентский ключ.

Изменение доступа перечитывается открытым приложением каждые 5 секунд и при возвращении на вкладку. Серверные правила проверяются на каждом запросе. Скрытие пункта меню не является механизмом защиты.

## PWA

Production содержит manifest, иконки и service worker. Установка использует возможности браузера; на iPhone — «Поделиться → На экран Домой». Новая версия устанавливается по кнопке после сохранения форм.

Кэшируются только сборочные JS/CSS/шрифты и нейтральный offline-экран. HTML сессии, API, токены, карточки клиентов и финансовые ответы в Cache Storage не сохраняются. Для изменения заказов требуется сеть. Push реализован; для production нужны VAPID, расписание доставки и подписка устройства. Порядок подключения и проверки — в [notification-setup.md](notification-setup.md). Установка PWA сама по себе уведомления не включает.

## Напоминания и внешние сервисы

`/api/send-reminders` требует корректный непустой `CRON_SECRET`. Расписание запуска и SMTP необходимо проверить отдельно. Реальный платёж и доставка письма не подтверждаются локальными SQL-тестами. Не направлять тестовые письма клиентам и не списывать деньги в рабочем аккаунте для технической проверки.

## Откат

При проблеме frontend вернуть предыдущую успешную сборку Vercel. Новые таблицы и данные не удалять: изменения базы преимущественно добавляют объекты. Старый frontend после ограничения чтения зарплат может потребовать совместимого исправления; не возвращать старые широкие права доступа ради восстановления интерфейса. Восстановление данных проводить по копии на отдельном проекте и переносить только после проверки расхождений.
