# Работы владельца и мастера

Новая модель хранит отдельные работы внутри одного заказа автомобиля. Каждой работе назначаются мастер, этап, порядок, чек-лист и условия оплаты. Одинаковый порядок позволяет параллельное выполнение разными мастерами; более поздний порядок ждёт проверки всех предыдущих работ. Один мастер учитывает активное время только на одной работе одновременно.

## Включение в основной проект

1. База должна содержать миграции по 027 включительно. Сначала сохраните резервную копию штатными средствами Supabase.
2. В SQL Editor проекта `stxfbarigoutglfqqhwi` выполните **один раз** весь файл `supabase/deploy/workflow_028_030.sql`. Он собирает миграции 028–030 в одну транзакцию. Не применяйте затем эти же три файла повторно.
3. Проверка: `select public.job_workflow_version();` возвращает `30`.
4. Разверните текущий код в основном Vercel-проекте `detail-flow1/detailflow`. Дополнительные переменные окружения для рабочего процесса не нужны. Service-role ключ остаётся только на сервере.
5. Обновите открытые сессии владельца и мастера. Если интерфейс уже развёрнут, он автоматически обнаружит версию базы при следующем обновлении данных. До установки миграции остаётся прежний интерфейс.

Пакет можно пересобрать: `node scripts/build-workflow-migration.mjs`. После применения через SQL Editor отметьте 028–030 в своём журнале миграций, прежде чем запускать автоматический migration runner.

## Что сохраняется и как считается зарплата

- Старые заказы получают одну работу; сумма заказа, согласованный процент/фикс и существующие начисления сохраняются. Выплаченные начисления сохраняют выплаченную сумму.
- Старые активные работы переводятся в паузу внутри новой карточки: неизвестное историческое время не выдумывается. Мастер нажимает «Продовжити», чтобы начать учёт нового активного времени.
- На новой работе применяется фикс услуги, иначе процент услуги, иначе базовый процент, иначе почасовая ставка. Явный нулевой процент — это 0, а не отсутствие настройки. Изменение ставок профиля не пересчитывает уже назначенные работы. Пока работа не начата, владелец может явно обновить её условия.
- Почасовая оплата считается по активному таймеру работы, исключая паузы. Это не автоматическая оплата всех часов присутствия на смене.
- Статусы календаря обновляются из работ автоматически: начало → «В роботі», подтверждение всех работ → «Завершено». Завершить запись в обход проверки нельзя; отмена записи разрешена только до начала работ.
- Сдача чек-листа создаёт очередь проверки. Возврат требует причины и сбрасывает отметки. Подтверждение требует двух отметок контроля качества, создаёт одно начисление и не создаёт кассового расхода.
- Фактическая выплата регистрируется отдельно, частями или целиком. Повтор запроса с тем же идентификатором не создаёт дубль. Выплату и связанную кассовую строку нельзя удалить из обычного интерфейса.
- Старые автоматически созданные строки «Нарахування:…» помечаются `is_accrual=true`, сохраняются для сверки и исключаются из текущего денежного потока. Они не доказывают фактическую выдачу денег. Перед первой реальной выплатой сверьте старые начисления с фактически выплаченной зарплатой; миграция не угадывает этот факт.

## Доступ и синхронизация

Изменения выполняются серверными RPC с проверкой роли, студии, версии работы и состояния смены. Мастер видит свои работы, историю, фото и начисления; ставки и финансы студии защищены от его изменений. Фото хранятся в закрытом bucket `job-photos` (JPG/PNG/WebP, до 8 МБ, до 12 на работу). Подписанные ссылки действуют 5 минут. Неиспользованный объект после сетевой ошибки сохраняется, поскольку ответ мог потеряться уже после успешной привязки фото.

Realtime дополняется обновлением раз в 5 секунд и при возвращении на вкладку. Ошибка загрузки сохраняет последнюю полную выборку и блокирует действия в новом кабинете до успешного обновления.

## Проверено локально

- TypeScript приложения и API, production build.
- Регрессионные тесты CSV/форм/дат/чисел/пагинации.
- Реальный PostgreSQL через PGlite: применение схемы и миграций, сохранение старой зарплаты, границы студий и ролей, чек-лист, возврат, повторное подтверждение, процентная/фиксированная/почасовая и нулевая оплата, частичные выплаты, защита от переплаты, смены/перерывы, несколько услуг календаря на одном авто, последовательность этапов, политики хранения фото.
- Браузерный сценарий на синтетических данных в `/__qa` → «Процес»: назначить → начать смену → выполнить → проверить → начислить 300 → выплатить 100 → увидеть остаток 200 у мастера. Мобильная ширина 390 px и настольная 1280 px.

Стенд использует локальное состояние, а тест базы — настоящие SQL-функции. Live Supabase Auth, доставку приглашений, загрузку фото через Storage HTTP API и соединение Realtime с production эти проверки не заменяют. После установки миграции нужен smoke-тест двумя реальными тестовыми аккаунтами; не используйте для пробных выплат реальные рабочие начисления.
